# Stage 06：边制作边学习路线

> 状态：工程路线 0～7 已完成；个人 L0～L7 练习仍须自行验证；配套[实现路线](stage-06-implementation-roadmap.md)和[中文演示指南](../data/stage-06-demo-guide.md)。
> 学习预算：约 5 小时，分散在 Week 8，每天至少 30～60 分钟。先完成当日最小功能，再用实际请求、失败案例或审计解释原理；个人掌握程度不因测试通过而自动标记完成。

## 学习方法与节奏

每天遵循“预测行为 → 运行最小例子 → 对照证据 → 复述原因”。不要为看完课程停下项目，也不要只让 Agent 写代码而自己不会解释。优先阅读仓库里的 `Stage05ReliableRunner`、`Stage05ApprovalWorkflow`、`api/main.py` 和对应测试；Streamlit 安装后用技能发现脚本定位**当前锁定版本**的参考文档。每条练习把命令、期望、实际结果和一句解释记在自己的学习笔记，提交到阶段文档的只有工程决策与可公开的证据，不贴原始数据或密钥。

## L0：本地环境与信任边界（0.5h）

**边做边学。** 画出“浏览器 → Streamlit → FastAPI → Stage 05 → Stage 04/政策索引/Ollama”的调用方向，标明哪些进程持有报告、审批检查点、模型文件和费用账本。对照[路线 0 门禁](../../reports/stage-06-route-0-preflight.md)：Streamlit 1.64.0 已锁定，Docker CLI 在路线 0 时尚未发现，路线 5 复查已安装但 Engine 未就绪；工程检查通过不等于个人已掌握信任边界。

**动手练习。** 逐项指出 `policy_as_of`、交易 ID、模型 digest、API 配置和审批哈希的来源。预测容器里访问 `127.0.0.1:11434` 会连到哪里，再说明为何需要明确的宿主服务地址和受控 allowlist。把 Stage 05 真实报告里的“模拟政策”“未校准分数”提示转换成 UI 必须展示的文案。

**自测。** 如果 Ollama 停止但 TF-IDF 索引正常，健康接口和调查请求各应如何表示？为什么不能将训练标签或原始 IEEE-CIS CSV 复制进镜像？

## L1：服务组合、状态与复用（0.5h）

**边做边学。** 读 `api/main.py` 的 Stage 02 依赖注入和 `src/graphrisk/agent/reliability.py` 的真实调用计数。理解 FastAPI 应复用一个已验证的业务运行器，而不是把 SQL、模型、检索和报告逻辑重写到 route handler。区分 `run_id`（读取调查）、`session_id`（审批线程）和 `report_sha256`（冻结内容）。

工程实现可对照[服务契约](../data/stage-06-service-contract.md)和[路线 1 验收](../../reports/stage-06-route-1-service-composition.md)；个人时序图与解释仍需自行完成。

**动手练习。** 画一次调查与批准的时序图，标出浏览器刷新、API 进程重启两个事件。预测两个事件后哪些状态仍可读、哪些会失效；在单进程内模拟相同批准重复提交和不同批准冲突。

**自测。** 为什么报告不能只放在 Streamlit `session_state`？为什么 `uvicorn --workers 2` 对现阶段同进程审批是错误的演示配置？

## L2：FastAPI 的 HTTP 与业务语义（0.5h）

**边做边学。** 从 `ReliableRun` 的状态枚举出发，亲自写出一张“业务结果 → HTTP 状态/错误码/前端文案”表。确认“调查成功但没有政策结论”与“模型服务不可用”是不同结果；OpenAPI schema 只能保证结构，引用正确性仍由 Stage 05 核验。

工程结果可对照[路线 2 验收](../../reports/stage-06-route-2-investigation-api.md)；个人练习再复做一次无政策 201、模型断连 503 和 API 存活 200/就绪 503 的区别。

**动手练习。** 用 fake 测试客户端分别提交正常交易、错数据源、不存在交易和模型不可用；在自动文档中找到请求字段、响应 schema 与错误码。解释为什么 API 返回的图邻居空列表不等于图工具失败。

**自测。** `partial_evidence` 是否适合显示为“欺诈确定”？当 `get_transaction` 找不到记录时为何不继续检索政策和调用模型？

## L3：人工审批与备注（0.5h）

**边做边学。** 对照 `src/graphrisk/agent/approval.py` 的 `interrupt`、`Command(resume=...)` 与报告哈希。理解 pending、approved、rejected、expired 的边界，以及同一进程检查点为何不能满足重启恢复。备注是对建议的人工决策说明，不是改写冻结报告的入口。

**动手练习。** 对一条真实或 fake 报告依次尝试：正确拒绝、重复拒绝、改哈希批准、过期批准。逐步记下状态与审计事件，确认外部处置次数为 0，并检查备注与 reviewer_id 是否进入决策审计。不要把演示 reviewer_id 误称为已认证身份。

**自测。** 为什么 UI 的“已批准”文字不能由按钮本身决定？报告正文改变后，旧批准为什么必须失效？

## L4：Streamlit 的 rerun、状态和证据展示（1h）

**边做边学。** 路线 0 将 Streamlit 锁入项目环境后，重新运行 `developing-with-streamlit` 的发现脚本，阅读匹配版本的布局、表单、session state 和缓存参考。将 API 作为唯一事实来源；Streamlit rerun 只重绘页面，不重新发起成本较高的调查。

**动手练习。** 用一条 `verified`、一条 `partial_evidence`、一条 `insufficient_evidence` 响应设计三个状态视图：模型分数旁写“未校准”，图邻居空与图服务失败使用不同状态，政策引用显示标题/版本/章节/片段与“模拟政策”。点击批准/拒绝前先显示待审报告哈希；刷新后从 API 读取最终状态。逐项检查组件刷新不会重复调用 Ollama。

**自测。** `st.session_state` 应保存什么、不应保存什么？如果真实报告引用存在但政策适用性仍需人工判断，界面应该怎样表达？

## L5：Docker Compose 与可移植运行（0.5h）

**边做边学。** 区分 `uv.lock`、构建上下文、镜像、容器、卷和运行时环境变量。理解宿主 Ollama 模型目录不应被打包进镜像；只读工件卷和写入报告目录要分开。本机已安装 Docker CLI/Compose，`compose config` 通过，但 Linux Engine 尚未启动；不能把 `compose.yaml` 存在或语法通过当作部署成功。

**动手练习。** 先用 `uv run --offline python scripts\run_stage06_local.py` 启动并查看两个健康端点；画出容器 API 经 `host.docker.internal` 调用宿主 Ollama 的路径。从 `compose.yaml` 找出本机端口、只读工件挂载、独立可写报告目录和健康检查；本项目没有 secret 注入或外部 API 密钥。Docker 可用后执行 `docker compose config`、`up --build -d`、`ps` 和 `down`，用相同 held-out 交易比较本地与容器的版本、引用和状态，不要求毫秒延迟相同。对照[路线 5 记录](../../reports/stage-06-route-5-local-compose.md)解释为什么静态检查仍不足以交付容器。

**自测。** 为什么端口只绑定本机？如果容器启动成功但读取不到当前 GraphSAGE checkpoint，Stage 06 能否标 Done？

## L6：50 案例的可信评估（1h）

**工程证据。** [路线 6 评估报告](../../reports/stage-06-route-6-agent-evaluation.md)记录 17+33 案的冻结哈希、分组指标、三例真实本地样本与早期评估器误判；个人手工复核仍需自行完成。

**边做边学。** 先读 Stage 05 的[17 案例冻结集](../../data/evaluation/stage05_agent_cases_v1.yaml)和[路线 7 验收](../../reports/stage-05-route-7-reliability-evaluation.md)。新增案例必须覆盖不同风险点，而不是只换交易 ID。固定测试集先冻结再运行，记录失败；只用开发案例改实现和阈值，避免在冻结集上挑答案。

**动手练习。** 从新增案例各挑一个输入错误、旧版误引、图部分证据、模型错误和审批错绑，手工预测工具调用、引用允许集合、最终分支和审批状态；运行后归类错误。手算一组 5 例的分支通过率、引用完整率和审批绕过率，再解释为什么 P50/P95、Token 与费用要在真实 provider 样本中单独报告。

**自测。** 17+33=50 是否自动代表评估充分？如果 33 例其实都只改变 ID，有什么问题？为什么 fake provider 的 100% 通过率不能当作真实模型准确率？

## L7：端到端演示与求职表达（0.5h）

**边做边学。** 把 Stage 06 的最终运行记录与 Stage 05 的真实验收对照，确认 API/UI 只是让同一受控证据链可用，而没有把未校准分数或模拟政策包装成真实决策系统。记住 Stage 05 当前同 ID 测试 PR-AUC：受控 XGBoost 0.129566、GraphSAGE 0.085999、融合 0.118062，不能宣称 GNN 提升了测试效果。

**动手练习。** 用 90 秒向面试官展示：输入交易与政策日期；三类证据与可追溯引用；模型服务不可用/无政策时如何表达；审批为何需要报告哈希；拒绝后为何没有自动处置；最后说出单进程、模拟政策、未校准分数和 50 案例范围的限制。录音或写稿后不看文档复述。

**自测。** 面试官问“这不就是固定脚本吗”“你如何证明 Agent 没有乱引政策”“服务重启后审批会怎样”时，能否拿出状态边、案例与审计回答？
